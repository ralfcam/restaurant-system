## Integration recipes

| Hours RPC complete-replace, local-only   | Snapshot `operating_windows` in `beforeAll`. Restore with filtered **TABLE** `insert` of snapshot rows, then `delete` leftover ids (never `replace_operating_windows` — that RPC wipes the week; insert-first so a failed restore cannot empty hours). Skip rewrite when sorted ids match. Call `assertIsolatedHoursMutationTarget()` (`lib/scheduling/hours-mutation-target.ts`) at the start of both `beforeAll` and `afterAll` — restore is itself a mutating write, and Vitest still runs `afterAll` after a failed `beforeAll`; the guard fails closed against the shared linked project instead of skipping. Test target is local Supabase, not the linked remote (baseline already defines the RPC).                                             | `tests/integration/scheduling/replace-operating-windows.integ.test.ts`                                                                               |
| Complete-replace multiset pin            | After the RPC call, `select` **all** rows unfiltered and assert `toHaveLength(p_windows.length)` (no leftover/duplicate rows survive the replace). Then, for each expected `p_windows` entry, consume a match via `findIndex` + `splice` on the fetched rows (comparing `day_of_week`, `is_closed`, `label`, `sort_order`, and `normalizeTime`'d times), and assert the remaining unmatched array is empty. Reusable recipe for pinning "replace produced exactly this multiset, no dupes/no extras" RPC behavior.                                                                                                                                                                                                                                      | `tests/integration/scheduling/replace-operating-windows.integ.test.ts`                                                                               |
| Local-isolated Data API DML denial       | docker `GRANT SELECT, INSERT, UPDATE, DELETE` onto postgres Dxtm defaults to reproduce the linked-remote privilege surface, then pin authenticated insert error plus update/delete non-persist; keep `DROP POLICY IF EXISTS` without `CREATE` so `db reset` still strips a restored FOR ALL.                                                                                                                                                                                                                                                                                                                                                                                                                                                            | `tests/integration/scheduling/replace-operating-windows.integ.test.ts` → "authenticated Data API cannot insert, update, or delete operating_windows" |
| Three-file catalog privilege lock        | Two-line `-- REAZED-###: ACRONYM` comment inline above GRANT/REVOKE in baseline, `20260825140000_operating_windows_privilege.sql`, and `20260827160000_public_catalog_privileges.sql` (name the table when a second catalog table shares the acronym); DROP then GRANT/REVOKE; reservations `GRANT INSERT` + `REVOKE SELECT, UPDATE, DELETE` + `DROP POLICY IF EXISTS "Allow public read reservations"` (no `CREATE`; no `GRANT SELECT ON TABLE reservations`); `blocked_dates`/`menu_items` `GRANT SELECT` + `REVOKE INSERT, UPDATE, DELETE`; live Data API plus SQL-substring assertions; pin STRICT integration to `127.0.0.1` keys from `npx supabase status` when `.env.local` is the linked remote.
