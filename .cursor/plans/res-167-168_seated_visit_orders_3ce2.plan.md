## Spec

- Source: extend existing `docs/specs/scheduling.md` (FP-13, FP-15, FP-15-COMPLETE, FP-15-UNAVAILABLE; FP-8 for merges) and `docs/specs/walk-in-seating.md` (WI-2 plus new WI-9, WI-10). `docs/specs/post-visit-review-email.md` already says no send when the reservation has no email and PV-4 says "queued only on transition to completed"; it needs no edit.
- Summary: a visit is one seated reservation (walk-ins included). `createKitchenOrder` resolves the table's (or active merge group's) single seated reservation server-side and stamps it on `orders.reservation_id`; none or two-or-more seated reservations are refused with typed errors (`{ error }` return, no write). The floor chip bill sums by `reservation_id`, so a newly seated visit starts at `CHF 0.00`. `reservations.source` is added (`online|staff|walk_in|external`, default `online`, CHECK, not guest-insertable, no backfill). `seatWalkIn` stamps `source = 'walk_in'` and returns the new id. The review email is not queued when the reservation has no address. `PosTerminal` shows a specific EN/FR toast for the not-seated refusal.
- Design decisions made in this work-order (so phases do not guess):
  - Typed errors are **returned**, not thrown (same convention as `updateTableState`'s `{ error }`): `createKitchenOrder` returns `{ error: "errors.pos.tableNotSeated" }` or `{ error: "errors.pos.tableAmbiguousVisit" }`; success keeps `{ id, orderNumber }`. Other failures still throw as today.
  - Seated lookup shape (so mocks and source agree): `db.from("reservations").select("id").eq("status", "seated").in("table_label", labels)` where `labels` is the table's label, expanded to every member label when the table belongs to an active merge (C6). Zero rows → `tableNotSeated`; two or more → `tableAmbiguousVisit`; one → stamp `reservation_id`. The reservation row, not `tables.status`, is the source of truth.
  - `orders.reservation_id UUID REFERENCES reservations(id)` (default `NO ACTION`: a visit's orders can never be orphaned or cascade-deleted) plus `CONSTRAINT orders_reservation_id_required CHECK (reservation_id IS NOT NULL) NOT VALID`. No backfill, no index. `reservations.source TEXT NOT NULL DEFAULT 'online' CONSTRAINT reservations_source_check CHECK (source IN ('online','staff','walk_in','external'))`; the existing guest INSERT column grant line stays byte-identical.
  - The new dated migration is `supabase/migrations/20261015190000_orders_reservation_id_reservation_source.sql`, idempotent (`ADD COLUMN IF NOT EXISTS`, `DROP CONSTRAINT IF EXISTS` then `ADD CONSTRAINT`), tagged `-- RES-167`, and the same statements are folded into `supabase/migrations/00000000000000_baseline.sql` (repo convention). Existing migrations are otherwise not edited. `orders` stays service-role-only (no new policy or grant).
  - `lib/floor/table-bills.ts` exports `sumOpenOrderTotalsByReservationId(orders: { reservation_id: string | null; total: number; status: string }[]): Record<string, number>` replacing `sumOpenOrderTotalsByTableLabel`; rows with a null `reservation_id` are ignored. `FloorSnapshot.tableTotals` becomes `Record<reservationId, number> | null`. `overlayReservationsOnTables` reads `tableTotals[reservation.id] ?? 0` for a seated overlay.
  - Message keys: `errors.pos.tableNotSeated` (EN "Orders can only be sent for a seated table. Seat the guest first, then try again." / FR "Les commandes ne peuvent être envoyées que pour une table occupée. Installez d'abord le convive, puis réessayez."), `errors.pos.tableAmbiguousVisit`, `staff.pos.tableNotSeatedTitle` (EN "Table {label} has no seated guest" / FR "Aucun convive installé à la table n° {label}"), `staff.pos.tableNotSeatedDescription` (same text as `errors.pos.tableNotSeated`). `tableAmbiguousVisit` maps to today's generic `staff.pos.sendFailed` toast in `PosTerminal`.
  - `updateTableState` is NOT changed (the available-to-seated gap is closed by the `createKitchenOrder` refusal).
  - Known gotcha to measure, not paper over: a `NOT VALID` CHECK is still evaluated on UPDATE of a legacy row whose `reservation_id` is NULL, so a pre-release open kitchen order cannot change status. The brief accepts the NOT VALID design and its release note; this is reported to Jose as an open item with the observed behavior (Criterion C1 Green records it), the constraint is not weakened.
- Clarifications needed: none blocking. Non-blocking: `source` values `staff` and `external` stay unused by writers in this PR (briefs only require `walk_in` and the default `online`); listed as a finding.
